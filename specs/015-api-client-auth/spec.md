# Feature Specification: API Client & Auth Flow

**Feature Branch**: `015-api-client-auth`
**Created**: 2026-02-07
**Status**: Draft
**Input**: Integration module — HTTP client, JWT interceptors, auth context/provider, protected routes, token refresh logic. Замена mock auth на реальный backend.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вход в систему с реальным бэкендом (Priority: P1)

Зарегистрированный пользователь открывает страницу входа, вводит email и пароль. Система отправляет данные на сервер, получает токены авторизации, сохраняет их и перенаправляет пользователя на главную страницу (dashboard). При последующих запросах к серверу токен автоматически подставляется в заголовки.

**Why this priority**: Вход — базовое действие, без которого невозможна работа с любыми защищёнными функциями приложения. Это фундамент для всех остальных интеграций.

**Independent Test**: Можно проверить, открыв страницу логина, введя валидные учётные данные и убедившись, что пользователь попадает на dashboard с корректными данными профиля.

**Acceptance Scenarios**:

1. **Given** пользователь на странице входа, **When** вводит корректные email/пароль и нажимает "Войти", **Then** система отправляет запрос на сервер, сохраняет полученные токены, перенаправляет на /dashboard и отображает данные пользователя
2. **Given** пользователь на странице входа, **When** вводит неверные учётные данные, **Then** отображается уведомление об ошибке "Invalid credentials" без перенаправления
3. **Given** пользователь на странице входа, **When** учётная запись заблокирована (5+ неудачных попыток), **Then** отображается уведомление о блокировке аккаунта
4. **Given** кнопка "Войти" нажата, **When** запрос обрабатывается, **Then** кнопка показывает состояние загрузки и блокируется от повторного нажатия

---

### User Story 2 - Регистрация нового аккаунта (Priority: P1)

Новый пользователь открывает страницу регистрации, заполняет форму (имя, email, пароль) и создаёт аккаунт. Система регистрирует его на сервере, получает токены и перенаправляет на dashboard.

**Why this priority**: Регистрация — второй критичный сценарий входа в систему. Без неё нет притока новых пользователей.

**Independent Test**: Открыть страницу регистрации, заполнить форму новыми данными и убедиться, что аккаунт создан и пользователь попадает на dashboard.

**Acceptance Scenarios**:

1. **Given** пользователь на странице регистрации, **When** заполняет все обязательные поля валидными данными и отправляет форму, **Then** создаётся аккаунт, сохраняются токены, пользователь перенаправляется на /dashboard
2. **Given** пользователь на странице регистрации, **When** вводит email, который уже зарегистрирован, **Then** отображается уведомление об ошибке "Email already registered"
3. **Given** пользователь на странице регистрации, **When** пароль не соответствует требованиям (менее 8 символов, без заглавной буквы, числа или спецсимвола), **Then** ошибка валидации отображается на клиенте до отправки на сервер

---

### User Story 3 - Автоматическое продление сессии (Priority: P1)

Пользователь работает в приложении. Когда его токен доступа истекает (через 15 минут), система автоматически обновляет его в фоне, используя refresh token. Пользователь не замечает обновления — текущий запрос повторяется с новым токеном.

**Why this priority**: Без автоматического обновления токена пользователь будет принудительно разлогинен каждые 15 минут, что делает приложение непригодным для работы.

**Independent Test**: Войти в систему, подождать истечения access token (или симулировать получение 401 ответа), убедиться, что запрос повторяется успешно без участия пользователя.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован и access token истёк, **When** приложение делает запрос к серверу и получает 401, **Then** система автоматически обновляет токены через refresh endpoint и повторяет оригинальный запрос
2. **Given** refresh token тоже истёк или невалиден, **When** попытка обновления возвращает ошибку, **Then** токены очищаются, пользователь перенаправляется на /login
3. **Given** несколько запросов одновременно получают 401, **When** начинается процесс обновления токена, **Then** все ожидающие запросы получают новый токен, а не инициируют множественные refresh-вызовы

---

### User Story 4 - Защита маршрутов от неавторизованных (Priority: P2)

Неавторизованный пользователь пытается открыть защищённую страницу (dashboard, projects, templates, settings). Система перенаправляет его на страницу входа. После успешного входа пользователь попадает на исходно запрошенную страницу.

**Why this priority**: Защита маршрутов — необходимая часть безопасности, но она зависит от работающего механизма входа (P1 stories).

**Independent Test**: Открыть /dashboard в новом браузере без авторизации и убедиться в перенаправлении на /login. Затем войти и проверить перенаправление обратно.

**Acceptance Scenarios**:

1. **Given** неавторизованный пользователь, **When** пытается открыть /dashboard, /projects, /templates или /settings, **Then** перенаправляется на /login
2. **Given** авторизованный пользователь, **When** открывает защищённую страницу, **Then** страница загружается нормально
3. **Given** авторизованный пользователь, **When** пытается открыть /login или /register, **Then** перенаправляется на /dashboard
4. **Given** неавторизованный пользователь перенаправлен на /login, **When** успешно входит, **Then** перенаправляется на исходно запрошенную страницу (а не всегда на /dashboard)
5. **Given** страница загружается, **When** проверка авторизации ещё выполняется, **Then** показывается скелетон загрузки, а не мерцание контента

---

### User Story 5 - Выход из системы (Priority: P2)

Авторизованный пользователь нажимает кнопку "Выйти". Система отзывает токены на сервере, очищает локальное хранилище и перенаправляет на страницу входа.

**Why this priority**: Выход — стандартная функция безопасности, важная для многопользовательских устройств.

**Independent Test**: Войти, нажать "Выйти", убедиться в перенаправлении на /login. Попытаться вернуться на /dashboard — должен быть перенаправлен на /login.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** нажимает "Выйти", **Then** токены отзываются на сервере, локальные данные очищаются, пользователь перенаправляется на /login
2. **Given** пользователь вышел, **When** пытается использовать кнопку "Назад" в браузере для возврата на защищённую страницу, **Then** перенаправляется на /login

---

### User Story 6 - Восстановление пароля (Priority: P3)

Пользователь забыл пароль, запрашивает восстановление через email. Система отправляет письмо со ссылкой для сброса.

**Why this priority**: Важная функция для UX, но не блокирует основной рабочий процесс. Пользователи могут обратиться в поддержку как временное решение.

**Independent Test**: Ввести email на странице восстановления пароля и убедиться в отображении сообщения "Проверьте вашу почту".

**Acceptance Scenarios**:

1. **Given** пользователь на странице восстановления пароля, **When** вводит зарегистрированный email и отправляет форму, **Then** отображается сообщение об успешной отправке письма
2. **Given** пользователь на странице восстановления пароля, **When** вводит незарегистрированный email, **Then** отображается такое же сообщение успеха (не раскрывать, зарегистрирован ли email — требование безопасности)

---

### Edge Cases

- Что происходит при потере интернет-соединения во время входа/регистрации? — Отображается уведомление "Нет соединения с сервером" с возможностью повторить попытку
- Что если пользователь открывает приложение в двух вкладках и выходит в одной? — Вторая вкладка при следующем запросе обнаружит отсутствие валидных токенов и перенаправит на /login
- Что если сервер недоступен (500 ошибка) при попытке refresh token? — Система не разлогинивает пользователя немедленно; оригинальный запрос завершается с ошибкой, но токены сохраняются для следующей попытки
- Что если пользователь вручную удалит cookies/localStorage? — При следующем запросе система обнаружит отсутствие токена и перенаправит на /login
- Что если access token и refresh token оба валидны, но пользователь был деактивирован на сервере? — Сервер вернёт 403, система должна разлогинить пользователя и перенаправить на /login с уведомлением

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять единый настроенный HTTP-клиент для всех запросов к серверу с автоматическим добавлением токена авторизации
- **FR-002**: Система ДОЛЖНА сохранять пару токенов (access + refresh) после успешного входа или регистрации
- **FR-003**: Система ДОЛЖНА автоматически подставлять access token в заголовок Authorization каждого запроса к защищённым эндпоинтам
- **FR-004**: Система ДОЛЖНА автоматически обновлять access token при получении ответа 401 от сервера, используя refresh token
- **FR-005**: Система ДОЛЖНА повторять оригинальный запрос после успешного обновления токена, прозрачно для пользователя
- **FR-006**: Система ДОЛЖНА очищать все токены и перенаправлять на /login, если обновление refresh token завершается ошибкой
- **FR-007**: Система ДОЛЖНА предотвращать множественные параллельные запросы на обновление токена (queue pending requests)
- **FR-008**: Система ДОЛЖНА предоставлять глобальный контекст авторизации, доступный всем компонентам приложения (user, isLoading, isAuthenticated, login, register, logout)
- **FR-009**: Система ДОЛЖНА проверять наличие действующей сессии при загрузке приложения (запрос профиля пользователя)
- **FR-010**: Система ДОЛЖНА блокировать доступ к защищённым маршрутам (/dashboard, /projects, /templates, /settings) для неавторизованных пользователей
- **FR-011**: Система ДОЛЖНА перенаправлять авторизованных пользователей с /login и /register на /dashboard
- **FR-012**: Система ДОЛЖНА показывать состояние загрузки (скелетон) пока проверяется авторизация, исключая мерцание контента
- **FR-013**: Система ДОЛЖНА отображать ошибки сервера через toast-уведомления с понятными сообщениями
- **FR-014**: Система ДОЛЖНА поддерживать redirect на исходно запрошенную страницу после успешного входа
- **FR-015**: Система ДОЛЖНА корректно обрабатывать ответ сервера в формате `{ data: {...} }`, маппируя его на клиентские типы
- **FR-016**: Система ДОЛЖНА вызывать серверный endpoint /auth/logout для отзыва токенов при выходе пользователя
- **FR-017**: Система ДОЛЖНА ограничивать таймаут HTTP-запросов (30 секунд) для предотвращения зависаний

### Key Entities

- **User**: Представление авторизованного пользователя — идентификатор, email, имя, аватар, план подписки, баланс кредитов, реферальный код, статус верификации, дата создания, дата последнего входа
- **Auth Session**: Пара токенов (access + refresh), определяющая текущую сессию пользователя. Access token живёт 15 минут, refresh — 7 дней
- **Auth State**: Глобальное состояние авторизации в приложении — текущий пользователь, флаги загрузки и аутентификации, функции входа/регистрации/выхода

## Assumptions

- Токены хранятся в localStorage (access token) и localStorage (refresh token), т.к. бэкенд не выдаёт httpOnly cookies напрямую — токены возвращаются в теле JSON-ответа
- Формат ответа сервера для всех auth-эндпоинтов: `{ data: {...} }`
- Access token истекает через 15 минут, refresh token — через 7 дней (соответствует конфигурации бэкенда)
- Публичные маршруты: /, /login, /register, /forgot-password. Все остальные — защищённые
- При получении 403 (деактивированный аккаунт) пользователь разлогинивается аналогично 401 без возможности refresh
- Бэкенд использует ротацию refresh token — старый токен инвалидируется при обновлении

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может войти в систему и попасть на dashboard за менее чем 3 секунды при стабильном соединении
- **SC-002**: 100% запросов к защищённым эндпоинтам автоматически содержат валидный токен авторизации без участия пользователя
- **SC-003**: Обновление токена происходит незаметно для пользователя — ни один запрос не завершается ошибкой из-за истёкшего access token при валидном refresh token
- **SC-004**: Неавторизованный пользователь не может увидеть контент защищённых страниц ни при одном сценарии (прямой URL, кнопка "назад", ручная навигация)
- **SC-005**: Все ошибки аутентификации отображаются пользователю через toast-уведомления с понятными сообщениями в течение 1 секунды после получения ответа
- **SC-006**: После выхода из системы невозможно получить доступ к защищённым данным без повторного входа
