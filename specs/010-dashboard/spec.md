# Feature Specification: Dashboard

**Feature Branch**: `010-dashboard`
**Created**: 2026-02-06
**Status**: Draft
**Input**: User description: "Dashboard - главная страница после входа с welcome card, статистикой, быстрыми действиями, недавними проектами и daily bonus"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Приветствие и обзор аккаунта (Priority: P1)

Пользователь входит в систему и попадает на главную страницу, где видит персональное приветствие с именем и ключевую статистику своего аккаунта: количество кредитов с текущим планом, количество проектов из допустимого лимита и количество развёрнутых проектов. Числовые показатели анимируются от 0 до реального значения при первой загрузке страницы. Пользователь может сразу перейти к созданию нового проекта или пополнению кредитов.

**Why this priority**: Это первое, что видит пользователь после входа. Welcome card формирует первое впечатление, даёт понимание состояния аккаунта и мотивирует к действию. Без этого dashboard не несёт ценности.

**Independent Test**: Можно полностью протестировать, открыв dashboard — приветствие отображается, статистика анимируется, кнопки ведут на соответствующие страницы.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован, **When** открывает dashboard, **Then** видит приветствие со своим именем и три карточки статистики с анимацией count-up
2. **Given** пользователь на dashboard, **When** нажимает "Создать проект", **Then** переходит на страницу создания проекта
3. **Given** пользователь на dashboard, **When** нажимает "Пополнить кредиты", **Then** переходит на страницу пополнения кредитов
4. **Given** пользователь на мобильном устройстве, **When** открывает dashboard, **Then** карточки статистики адаптируются (горизонтальный скролл или вертикальный стек)

---

### User Story 2 - Недавние проекты (Priority: P2)

Пользователь видит до трёх последних проектов с их статусами и временем последнего изменения. Каждый проект кликабелен и ведёт на страницу проекта. Если проектов нет, отображается мотивирующий empty state с призывом создать первый бот.

**Why this priority**: Быстрый доступ к текущим проектам — основная повседневная потребность пользователя. Это снижает количество кликов до рабочего контекста.

**Independent Test**: Можно протестировать отдельно — при наличии проектов отображается grid с карточками, при отсутствии — empty state с CTA.

**Acceptance Scenarios**:

1. **Given** у пользователя есть проекты, **When** открывает dashboard, **Then** видит до 3 последних проектов в виде карточек со статусом и относительным временем
2. **Given** пользователь видит проект в списке, **When** кликает на карточку, **Then** переходит на страницу этого проекта
3. **Given** у пользователя нет проектов, **When** открывает dashboard, **Then** видит empty state с иллюстрацией и кнопкой "Создать проект"
4. **Given** пользователь видит список проектов, **When** нажимает "Все проекты", **Then** переходит на полный список проектов

---

### User Story 3 - Быстрые действия (Priority: P3)

Пользователь видит два популярных шаблона бота (Shop Bot и FAQ Bot) с бейджами и может сразу перейти к созданию проекта по выбранному шаблону. Карточки реагируют на наведение подъёмом и цветной линией сверху.

**Why this priority**: Ускоряет onboarding новых пользователей, предлагая готовые популярные шаблоны вместо пустой формы создания. Менее критично для returning users, которые уже имеют проекты.

**Independent Test**: Можно протестировать отдельно — карточки отображаются, hover-эффекты работают, клик ведёт к созданию проекта с выбранным шаблоном.

**Acceptance Scenarios**:

1. **Given** пользователь на dashboard, **When** видит секцию быстрых действий, **Then** отображаются 2 карточки шаблонов с бейджами
2. **Given** пользователь наводит на карточку шаблона, **When** курсор над карточкой, **Then** карточка поднимается и появляется градиентная линия сверху
3. **Given** пользователь кликает на карточку шаблона, **When** клик, **Then** переходит на страницу создания проекта с выбранным шаблоном

---

### User Story 4 - Daily Bonus (Priority: P4)

Пользователь видит информацию о ежедневном бонусе: можно ли его получить сегодня, текущую серию дней подряд и прогресс до двойного бонуса. Если бонус не получен — отображается кнопка для получения. После получения — информационный режим с зелёной галочкой.

**Why this priority**: Механика удержания (retention), которая мотивирует ежедневные визиты. Важна для бизнес-метрик, но не блокирует основной функционал dashboard.

**Independent Test**: Можно протестировать отдельно — два состояния (получен/не получен), прогресс-бар, streak counter, анимация при получении.

**Acceptance Scenarios**:

1. **Given** пользователь не получал бонус сегодня, **When** открывает dashboard, **Then** видит карточку с кнопкой "Получить" и информацией о количестве кредитов
2. **Given** пользователь не получал бонус, **When** нажимает "Получить", **Then** бонус зачисляется, отображается анимация подтверждения, кнопка заменяется на зелёную галочку
3. **Given** пользователь уже получил бонус сегодня, **When** открывает dashboard, **Then** видит информационную карточку со статусом "Получено" и данными о серии
4. **Given** пользователь копит серию дней, **When** смотрит прогресс-бар, **Then** видит заполнение от 0 до 7 дней и информацию о бонусе x2 на 7-й день

---

### User Story 5 - Анимации и визуальная привлекательность (Priority: P5)

При загрузке dashboard все секции появляются с анимацией fadeInUp с нарастающей задержкой, создавая эффект последовательного появления контента. Числа в welcome card анимируются от нуля. Анимации уважают системную настройку reduced motion.

**Why this priority**: Визуальная полировка, которая улучшает восприятие, но не влияет на функциональность.

**Independent Test**: Можно протестировать — при загрузке страницы секции появляются последовательно, при включённом reduced motion анимации отключаются.

**Acceptance Scenarios**:

1. **Given** пользователь загружает dashboard, **When** страница рендерится, **Then** секции появляются последовательно с эффектом fadeInUp
2. **Given** у пользователя включён reduced motion, **When** загружает dashboard, **Then** все элементы отображаются без анимаций

---

### Edge Cases

- Что происходит при очень длинном имени пользователя? Текст должен обрезаться с многоточием.
- Что если все числовые показатели равны нулю? Карточки отображаются корректно с нулями и мотивирующими подсказками.
- Что если количество проектов равно лимиту? Кнопка "Создать проект" должна информировать о достижении лимита.
- Что если серия daily bonus прерывается? Счётчик сбрасывается, пользователь видит актуальный прогресс.
- Что происходит при медленном соединении? Отображаются skeleton-загрузчики вместо данных.
- Что если пользователь не авторизован? Редирект на страницу входа.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА отображать персональное приветствие с именем авторизованного пользователя
- **FR-002**: Система ДОЛЖНА показывать три карточки статистики: баланс кредитов с планом, количество проектов из лимита, количество развёрнутых проектов из общего числа
- **FR-003**: Числовые показатели в карточках статистики ДОЛЖНЫ анимироваться от 0 до реального значения за 1 секунду при первой загрузке
- **FR-004**: Система ДОЛЖНА предоставлять кнопку "Создать проект" (gradient button) из welcome card
- **FR-005**: Система ДОЛЖНА предоставлять ссылку "Пополнить кредиты" из welcome card
- **FR-006**: Система ДОЛЖНА отображать до 3 последних проектов пользователя с именем, статусом (Deployed / Ready / Draft / Failed) и относительным временем
- **FR-007**: Каждая карточка проекта ДОЛЖНА быть кликабельной и вести на страницу проекта
- **FR-008**: При отсутствии проектов система ДОЛЖНА отображать empty state с иллюстрацией и CTA "Создать проект"
- **FR-009**: Система ДОЛЖНА отображать ссылку "Все проекты" в секции недавних проектов
- **FR-010**: Система ДОЛЖНА отображать 2 карточки быстрых действий: Shop Bot ("Самый популярный") и FAQ Bot ("Быстрый старт")
- **FR-011**: Карточки быстрых действий ДОЛЖНЫ реагировать на наведение анимацией подъёма и градиентной линией сверху
- **FR-012**: Клик по карточке быстрого действия ДОЛЖЕН вести к созданию проекта по выбранному шаблону
- **FR-013**: Система ДОЛЖНА отображать карточку daily bonus с текущим состоянием (получен/не получен)
- **FR-014**: Система ДОЛЖНА показывать streak counter (количество дней подряд) и прогресс-бар (N/7 дней до бонуса x2)
- **FR-015**: Если бонус не получен, система ДОЛЖНА показывать кнопку для его получения
- **FR-016**: После получения бонуса система ДОЛЖНА показать анимацию подтверждения и перейти в информационный режим
- **FR-017**: Все секции dashboard ДОЛЖНЫ появляться с анимацией fadeInUp с нарастающей задержкой
- **FR-018**: Анимации ДОЛЖНЫ уважать системную настройку reduced motion (prefers-reduced-motion)
- **FR-019**: Макет ДОЛЖЕН быть адаптивным: desktop (карточки в ряд) и mobile (стек или горизонтальный скролл)
- **FR-020**: Система ДОЛЖНА отображать skeleton-загрузчики при ожидании данных
- **FR-021**: Неавторизованные пользователи ДОЛЖНЫ быть перенаправлены на страницу входа

### Key Entities

- **User Profile**: Имя пользователя, текущий план, баланс кредитов, лимит проектов
- **Project Summary**: Имя проекта, статус (Deployed / Ready / Draft / Failed), время последнего обновления, идентификатор
- **Daily Bonus State**: Статус получения за сегодня, счётчик серии (streak), дата последнего получения
- **Template Shortcut**: Название шаблона, slug, бейдж-текст, emoji

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Dashboard полностью загружается и отображает все секции за менее чем 2 секунды
- **SC-002**: Пользователь может перейти к созданию проекта за 1 клик с dashboard
- **SC-003**: Пользователь может открыть любой из недавних проектов за 1 клик
- **SC-004**: 100% элементов интерфейса отображаются корректно на экранах от 320px до 2560px
- **SC-005**: Все интерактивные элементы имеют визуальный feedback при наведении и нажатии
- **SC-006**: Анимации воспроизводятся плавно (без jank) при 60fps
- **SC-007**: Механика daily bonus увеличивает частоту ежедневных возвратов пользователей

## Assumptions

- Для MVP данные пользователя берутся из mock data (auth store / mock API), реальная интеграция с бэкендом — в будущих модулях
- Daily bonus claim — локальная операция на клиенте для MVP, серверная верификация добавится позже
- Шаблоны быстрых действий зафиксированы (Shop Bot, FAQ Bot) и не загружаются динамически для MVP
- Существующие компоненты design system (FadeInUp, MainLayout, Card, Badge, Button, Shimmer) переиспользуются
- Страница dashboard доступна по пути `/dashboard`
