# Feature Specification: Projects Module

**Feature Branch**: `005-projects-module`
**Created**: 2026-02-05
**Status**: Draft
**Input**: User description: "Projects module for managing user projects (bots/APIs), CRUD operations, generation workflow, and status tracking"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create Project (Priority: P1)

Пользователь создаёт новый проект, выбирая шаблон и указывая название проекта. Проект начинается в статусе "черновик" и хранит конфигурацию пользователя.

**Why this priority**: Создание проекта — точка входа для всех последующих действий. Без возможности создать проект невозможно пользоваться системой.

**Independent Test**: Можно полностью протестировать, создав проект с названием, описанием, шаблоном и конфигурацией. Результат — сохранённый проект в статусе "draft".

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** он создаёт проект с валидным названием и шаблоном, **Then** система сохраняет проект со статусом "draft" и возвращает данные проекта
2. **Given** авторизованный пользователь, **When** он создаёт проект с пустым названием, **Then** система возвращает ошибку валидации
3. **Given** авторизованный пользователь, **When** он создаёт проект с несуществующим шаблоном, **Then** система возвращает ошибку "шаблон не найден"

---

### User Story 2 - View and Manage Projects (Priority: P1)

Пользователь просматривает список своих проектов с пагинацией и фильтрацией по статусу. Может открыть детали конкретного проекта.

**Why this priority**: Управление списком проектов критично для навигации по системе. Пользователь должен видеть все свои проекты и их текущие статусы.

**Independent Test**: Можно протестировать, создав несколько проектов и проверив, что все отображаются в списке с корректной пагинацией.

**Acceptance Scenarios**:

1. **Given** пользователь с 25 проектами, **When** он запрашивает список с пагинацией (страница 1, 20 на страницу), **Then** система возвращает 20 проектов и информацию о 2 страницах
2. **Given** пользователь с проектами в разных статусах, **When** он фильтрует по статусу "ready", **Then** система возвращает только проекты в этом статусе
3. **Given** пользователь, **When** он запрашивает детали своего проекта, **Then** система возвращает полную информацию включая конфигурацию и сгенерированный код

---

### User Story 3 - Update Project (Priority: P2)

Пользователь изменяет название, описание, конфигурацию или видимость проекта (публичный/приватный).

**Why this priority**: Редактирование проекта важно, но не критично для первичного использования системы.

**Independent Test**: Можно протестировать, создав проект и обновив его поля, проверив что изменения сохранились.

**Acceptance Scenarios**:

1. **Given** проект пользователя, **When** он обновляет название, **Then** система сохраняет новое название
2. **Given** проект пользователя, **When** он меняет видимость на публичную, **Then** проект становится доступен для публичного просмотра
3. **Given** проект другого пользователя, **When** пользователь пытается его обновить, **Then** система возвращает ошибку "проект не найден"

---

### User Story 4 - Delete Project (Priority: P2)

Пользователь удаляет ненужный проект.

**Why this priority**: Удаление проекта — важная функция для управления рабочим пространством, но не критична для основного workflow.

**Independent Test**: Можно протестировать, создав и удалив проект, проверив что он больше недоступен.

**Acceptance Scenarios**:

1. **Given** проект пользователя, **When** он удаляет проект, **Then** проект удаляется и больше недоступен
2. **Given** проект другого пользователя, **When** пользователь пытается его удалить, **Then** система возвращает ошибку "проект не найден"

---

### User Story 5 - Trigger Code Generation (Priority: P1)

Пользователь запускает генерацию кода для проекта. Система меняет статус на "generating" и делегирует генерацию AI-модулю.

**Why this priority**: Генерация кода — ключевая ценность продукта. Это главная функция для которой пользователи создают проекты.

**Independent Test**: Можно протестировать, создав проект и запустив генерацию, проверив смену статуса на "generating".

**Acceptance Scenarios**:

1. **Given** проект в статусе "draft", **When** пользователь запускает генерацию, **Then** статус меняется на "generating"
2. **Given** проект в статусе "generating", **When** пользователь пытается запустить генерацию повторно, **Then** система возвращает ошибку
3. **Given** проект в статусе "ready", **When** пользователь пытается запустить генерацию, **Then** система возвращает ошибку

---

### User Story 6 - Access Control (Priority: P1)

Пользователь может получить доступ только к своим проектам. Другие пользователи не видят чужие приватные проекты.

**Why this priority**: Безопасность и приватность данных — критичные требования для любой системы с пользовательским контентом.

**Independent Test**: Можно протестировать, создав проект одним пользователем и попытавшись получить к нему доступ другим.

**Acceptance Scenarios**:

1. **Given** приватный проект пользователя A, **When** пользователь B пытается его просмотреть, **Then** система возвращает ошибку "проект не найден"
2. **Given** публичный проект пользователя A, **When** пользователь B пытается его просмотреть, **Then** система возвращает данные проекта (только чтение)

---

### Edge Cases

- Что происходит при создании проекта с максимальной длиной названия (255 символов)?
- Как система обрабатывает удаление шаблона, связанного с существующими проектами?
- Что происходит при одновременном обновлении проекта из двух сессий?
- Как обрабатывается ошибка генерации (статус "error")?
- Что происходит при попытке создать проект с невалидной конфигурацией относительно схемы шаблона?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять авторизованным пользователям создавать проекты с названием (1-255 символов), опциональным описанием и обязательной связью с шаблоном
- **FR-002**: Система ДОЛЖНА сохранять каждый новый проект в статусе "draft"
- **FR-003**: Система ДОЛЖНА позволять сохранять пользовательскую конфигурацию проекта в формате ключ-значение
- **FR-004**: Система ДОЛЖНА предоставлять пагинированный список проектов пользователя (по умолчанию 20 на страницу, максимум 100)
- **FR-005**: Система ДОЛЖНА поддерживать фильтрацию списка проектов по статусу
- **FR-006**: Система ДОЛЖНА сортировать список проектов по дате создания (новые первыми)
- **FR-007**: Система ДОЛЖНА возвращать полную информацию о проекте включая сгенерированный код при запросе деталей
- **FR-008**: Система ДОЛЖНА позволять владельцу обновлять название, описание, конфигурацию и видимость проекта
- **FR-009**: Система ДОЛЖНА позволять владельцу удалять проект
- **FR-010**: Система ДОЛЖНА ограничивать доступ к проекту только его владельцу (для приватных проектов)
- **FR-011**: Система ДОЛЖНА позволять публичный просмотр проектов с флагом is_public=true
- **FR-012**: Система ДОЛЖНА поддерживать жизненный цикл статусов: draft → generating → ready → deploying → deployed, с возможностью перехода в error из любого состояния
- **FR-013**: Система ДОЛЖНА позволять запуск генерации только для проектов в статусе "draft"
- **FR-014**: Система ДОЛЖНА хранить сгенерированный код в структурированном формате (файлы с путями и содержимым)
- **FR-015**: Система ДОЛЖНА записывать информацию об использованной AI-модели при генерации
- **FR-016**: Система ДОЛЖНА хранить логи генерации для диагностики
- **FR-017**: Система ДОЛЖНА записывать временные метки: создания, обновления, генерации, деплоя

### Key Entities

- **Project**: Основная сущность, представляющая пользовательский проект. Содержит: идентификатор, связь с пользователем, название, описание, связь с шаблоном, конфигурацию, сгенерированный код, статус жизненного цикла, информацию о деплое, флаг публичности, временные метки.

- **ProjectStatus**: Перечисление статусов жизненного цикла проекта: draft (черновик), generating (генерация), ready (готов), deploying (деплой), deployed (задеплоен), error (ошибка).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может создать проект за менее чем 5 секунд (время отклика системы)
- **SC-002**: Система возвращает список из 100 проектов за менее чем 1 секунду
- **SC-003**: 100% запросов к чужим приватным проектам возвращают ошибку "не найден"
- **SC-004**: Все CRUD операции (создание, чтение, обновление, удаление) завершаются успешно с первой попытки при валидных данных
- **SC-005**: Переходы статусов проекта соответствуют определённому жизненному циклу в 100% случаев
- **SC-006**: Пользователь может найти нужный проект в списке за менее чем 10 секунд благодаря фильтрации и пагинации

## Assumptions

- Модуль Templates уже реализован и предоставляет валидные шаблоны для связи с проектами
- Модуль Auth уже реализован и предоставляет авторизованного пользователя через dependency injection
- AI-модуль будет реализован отдельно и будет вызываться асинхронно при генерации
- Deploy-модуль будет реализован отдельно и будет управлять статусами deploying/deployed
- Мягкое удаление (soft delete) не требуется для MVP — используется жёсткое удаление
- Валидация конфигурации против схемы шаблона будет реализована в рамках этого модуля
