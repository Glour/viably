# Feature Specification: Data Hooks (React Query Integration)

**Feature Branch**: `016-data-hooks`
**Created**: 2026-02-07
**Status**: Draft
**Input**: User description: "React Query hooks для всех API сущностей: users, templates, projects, credits. Замена mock data на реальный API. Кэширование, оптимистичные обновления, error handling."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Настройка инфраструктуры кэширования данных (Priority: P1)

Система управления данными инициализируется при загрузке приложения и обеспечивает единообразное кэширование, обработку ошибок и повторные попытки для всех API-запросов. Определена конвенция именования ключей кэша для всех сущностей.

**Why this priority**: Это техническая основа, без которой невозможна реализация всех остальных пользовательских историй. Должна быть реализована первой.

**Independent Test**: Проверить, что приложение запускается без ошибок с настроенной системой кэширования, и данные кэшируются корректно между переходами по страницам.

**Acceptance Scenarios**:

1. **Given** приложение загружается, **When** root layout инициализируется, **Then** система кэширования данных активна и готова к работе
2. **Given** запрос к API завершился ошибкой, **When** прошло время ожидания, **Then** система автоматически повторяет запрос один раз
3. **Given** данные были загружены менее 5 минут назад, **When** компонент запрашивает те же данные, **Then** данные берутся из кэша без обращения к серверу
4. **Given** кэш данных устарел (старше 10 минут), **When** компонент запрашивает эти данные, **Then** старые данные удаляются из памяти

---

### User Story 2 - Отображение реальных данных пользователя и кредитов (Priority: P1)

Авторизованный пользователь входит в приложение и видит актуальные данные: своё имя, баланс кредитов, информацию о плане подписки. Эти данные загружаются с сервера и кэшируются для быстрого доступа. При повторных визитах данные подтягиваются из кэша и обновляются в фоне.

**Why this priority**: Без реальных данных пользователя и кредитов приложение не функционально — навбар, дашборд и все страницы зависят от этой информации.

**Independent Test**: Открыть приложение после авторизации и проверить, что навбар показывает реальное имя пользователя и баланс кредитов из API.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован, **When** он открывает любую страницу приложения, **Then** навбар отображает его реальное имя и баланс кредитов
2. **Given** данные уже загружены, **When** пользователь переходит между страницами, **Then** данные отображаются мгновенно из кэша без повторного запроса
3. **Given** API недоступен, **When** пользователь пытается загрузить страницу, **Then** отображается состояние ошибки с возможностью повторить запрос
4. **Given** данные загружаются, **When** пользователь видит страницу, **Then** отображаются скелетон-заглушки вместо данных

---

### User Story 3 - Дашборд с актуальными данными (Priority: P1)

Пользователь открывает дашборд и видит реальную статистику: приветственную карточку с именем и планом, последние проекты, быстрые действия с популярными шаблонами, ежедневный бонус кредитов.

**Why this priority**: Дашборд — главная страница приложения, точка входа для всех пользователей. Замена mock данных на реальные критична для работоспособности продукта.

**Independent Test**: Открыть дашборд и убедиться, что все карточки отображают данные из API, а кнопка ежедневного бонуса работает.

**Acceptance Scenarios**:

1. **Given** пользователь на дашборде, **When** страница загрузилась, **Then** приветственная карточка показывает реальное имя, план и количество кредитов
2. **Given** у пользователя есть проекты, **When** он видит секцию "Последние проекты", **Then** отображаются до 3 последних проектов с актуальными данными
3. **Given** у пользователя нет проектов, **When** он видит секцию "Последние проекты", **Then** отображается пустое состояние с предложением создать первый проект
4. **Given** ежедневный бонус не получен, **When** пользователь нажимает "Получить бонус", **Then** баланс кредитов обновляется оптимистично (мгновенно в UI), а затем подтверждается сервером
5. **Given** бонус уже получен сегодня, **When** пользователь видит секцию бонуса, **Then** кнопка неактивна и показывает время до следующего бонуса

---

### User Story 4 - Галерея шаблонов из API (Priority: P2)

Пользователь открывает галерею шаблонов и видит актуальные шаблоны, загруженные с сервера. Может фильтровать по категории, искать по названию. При выборе шаблона видит полную информацию и может начать создание проекта.

**Why this priority**: Шаблоны — стартовая точка для создания проектов. Подключение к реальным данным позволяет администраторам управлять каталогом шаблонов без пересборки фронтенда.

**Independent Test**: Открыть галерею шаблонов, применить фильтр по категории и поиск, убедиться, что результаты приходят из API.

**Acceptance Scenarios**:

1. **Given** пользователь на странице шаблонов, **When** страница загружена, **Then** отображаются карточки шаблонов из API
2. **Given** пользователь выбирает категорию, **When** фильтр применяется, **Then** отображаются только шаблоны выбранной категории
3. **Given** пользователь вводит поисковый запрос, **When** прошла задержка после ввода (debounce), **Then** список шаблонов фильтруется по запросу
4. **Given** пользователь открывает детальную страницу шаблона, **When** данные загружены, **Then** отображается полная информация включая конфигурационные поля
5. **Given** пользователь нажимает "Создать проект" на странице шаблона, **When** проект успешно создан, **Then** пользователь перенаправляется на страницу генерации нового проекта

---

### User Story 5 - Управление проектами через API (Priority: P2)

Пользователь видит список своих проектов с реальными данными, может фильтровать, сортировать и искать. Может удалять и дублировать проекты. На странице проекта видит реальный код, логи и настройки.

**Why this priority**: Проекты — основная ценность продукта. CRUD-операции с реальным API необходимы для полноценной работы.

**Independent Test**: Открыть список проектов, применить фильтры, открыть детальную страницу проекта, проверить работу удаления и дублирования.

**Acceptance Scenarios**:

1. **Given** пользователь на странице проектов, **When** страница загружена, **Then** отображается список реальных проектов с фильтрами и сортировкой
2. **Given** пользователь фильтрует по статусу, **When** фильтр выбран, **Then** список показывает только проекты с этим статусом
3. **Given** пользователь удаляет проект, **When** удаление подтверждено, **Then** проект исчезает из списка оптимистично (мгновенно), показывается уведомление
4. **Given** пользователь дублирует проект, **When** операция завершена, **Then** пользователь перенаправляется на новый проект, список обновляется
5. **Given** пользователь на детальной странице проекта, **When** он переключает табы, **Then** загружается код (для редактора), логи или настройки окружения
6. **Given** пользователь ищет проект, **When** вводит текст в поле поиска, **Then** список проектов фильтруется по совпадению

---

### User Story 6 - История транзакций кредитов с пагинацией (Priority: P3)

Пользователь может просмотреть историю всех операций с кредитами: начисления, списания, покупки. Список подгружается постранично при прокрутке.

**Why this priority**: Дополнительная функциональность для прозрачности работы с кредитами. Не блокирует основные сценарии.

**Independent Test**: Открыть историю транзакций, прокрутить вниз и убедиться, что подгружаются новые записи.

**Acceptance Scenarios**:

1. **Given** пользователь открывает историю транзакций, **When** данные загружены, **Then** отображается первая страница транзакций
2. **Given** есть ещё транзакции, **When** пользователь прокручивает до конца списка, **Then** автоматически загружается следующая страница
3. **Given** пользователь фильтрует по типу транзакции, **When** фильтр применён, **Then** отображаются только транзакции выбранного типа

---

### User Story 7 - Редактирование профиля и смена пароля (Priority: P3)

Пользователь может обновить своё имя и аватар, а также сменить пароль. Изменения сохраняются через API.

**Why this priority**: Управление профилем — вспомогательная функция, не блокирующая основные рабочие процессы.

**Independent Test**: Изменить имя в настройках профиля, убедиться что обновлённое имя отображается в навбаре.

**Acceptance Scenarios**:

1. **Given** пользователь в настройках профиля, **When** он изменяет имя и сохраняет, **Then** имя обновляется в навбаре и на дашборде
2. **Given** пользователь вводит текущий и новый пароль, **When** он сохраняет, **Then** пароль обновляется и показывается уведомление об успехе
3. **Given** пользователь вводит неверный текущий пароль, **When** он пытается сохранить, **Then** отображается ошибка валидации

---

### Edge Cases

- Что происходит, когда токен авторизации истёк во время работы пользователя? — Система должна попытаться обновить токен, а при неудаче перенаправить на страницу входа
- Что происходит при потере интернет-соединения? — Кэшированные данные остаются доступны, новые запросы показывают ошибку с возможностью повтора
- Что происходит при одновременном обновлении данных из нескольких вкладок? — Каждая вкладка работает с собственным кэшем, при фокусе данные не перезапрашиваются автоматически (refetchOnWindowFocus отключён)
- Что происходит при оптимистичном удалении проекта, если сервер возвращает ошибку? — Проект возвращается в список, показывается уведомление об ошибке
- Что происходит если API возвращает пустой список шаблонов? — Отображается пустое состояние с информативным сообщением
- Что происходит при попытке получить ежедневный бонус повторно? — Сервер отклоняет запрос, UI показывает что бонус уже получен

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставить централизованную инфраструктуру кэширования данных с конфигурируемыми параметрами: время актуальности, время жизни кэша, количество повторных попыток
- **FR-002**: Система MUST использовать единообразную конвенцию именования ключей кэша для всех сущностей (пользователи, шаблоны, проекты, кредиты)
- **FR-003**: Система MUST загружать данные текущего пользователя (имя, аватар, план) и предоставлять их всем компонентам
- **FR-004**: Система MUST загружать баланс кредитов (количество, план, статус ежедневного бонуса, серия дней) и предоставлять данные для навбара и дашборда
- **FR-005**: Система MUST предоставлять возможность получения ежедневного бонуса с оптимистичным обновлением интерфейса
- **FR-006**: Система MUST загружать список шаблонов с поддержкой фильтрации по категории и сортировки
- **FR-007**: Система MUST загружать детальную информацию о шаблоне включая схему конфигурации
- **FR-008**: Система MUST предоставлять CRUD-операции для проектов: создание, чтение списка, чтение деталей, удаление, дублирование
- **FR-009**: Система MUST поддерживать фильтрацию проектов по статусу, сортировку и текстовый поиск
- **FR-010**: Система MUST загружать код проекта (список файлов с содержимым) для отображения в редакторе кода
- **FR-011**: Система MUST загружать логи проекта для отображения в табе логов
- **FR-012**: Система MUST предоставлять обновление переменных окружения проекта
- **FR-013**: Система MUST поддерживать постраничную загрузку истории транзакций кредитов (бесконечная прокрутка)
- **FR-014**: Система MUST предоставлять обновление профиля пользователя (имя, аватар)
- **FR-015**: Система MUST предоставлять смену пароля с проверкой текущего пароля
- **FR-016**: Система MUST инвалидировать связанные кэши после мутаций (например, после удаления проекта обновляется список проектов)
- **FR-017**: Система MUST отображать скелетон-заглушки при загрузке данных на всех страницах
- **FR-018**: Система MUST отображать состояние ошибки с возможностью повторного запроса при недоступности API
- **FR-019**: Система MUST выполнять оптимистичное обновление при удалении проекта (элемент исчезает из списка сразу, до подтверждения сервером)
- **FR-020**: Шаблоны MUST кэшироваться с увеличенным временем актуальности (30 минут), поскольку они обновляются редко
- **FR-021**: Система MUST показывать уведомления пользователю при успешных мутациях (получение бонуса, удаление проекта) и при ошибках

### Key Entities

- **User Profile**: Текущий пользователь — имя, аватар, план подписки. Используется во всём приложении (навбар, дашборд, настройки)
- **Credit Balance**: Баланс кредитов — количество, название плана, статус ежедневного бонуса, серия дней. Отображается в навбаре и на дашборде
- **Credit Transaction**: Запись транзакции кредита — тип, сумма, дата. Список с пагинацией
- **Template**: Шаблон — название, категория, описание, схема конфигурации. Статичные данные, длинный кэш
- **Project**: Проект — название, статус, шаблон, конфигурация, код, логи, переменные окружения. Основная рабочая сущность
- **Query Cache Key**: Иерархический ключ кэша — позволяет инвалидировать отдельные запросы или целые группы (все проекты, конкретный проект)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Все страницы приложения (дашборд, шаблоны, проекты) отображают реальные данные из API вместо заглушек
- **SC-002**: Повторные просмотры одних и тех же данных в рамках сессии не вызывают дополнительных запросов к серверу в течение настроенного времени кэширования
- **SC-003**: При переходе между страницами данные отображаются мгновенно (из кэша), без видимой задержки
- **SC-004**: Оптимистичные обновления (удаление проекта, получение бонуса) отражаются в интерфейсе менее чем за 100мс, до ответа сервера
- **SC-005**: При ошибке API пользователь видит информативное сообщение и может повторить запрос одним действием
- **SC-006**: 100% мутаций (создание, удаление, обновление) корректно инвалидируют связанные кэши, обеспечивая актуальность данных
- **SC-007**: Скелетон-заглушки отображаются на всех страницах во время первоначальной загрузки данных
- **SC-008**: Бесконечная прокрутка транзакций подгружает следующую страницу данных без перезагрузки всего списка

## Assumptions

- API-эндпоинты (users, templates, projects, credits) уже реализованы на бэкенде и соответствуют описанным интерфейсам
- Аутентификация через токены уже реализована (модуль 015-api-client-auth) и HTTP-клиент автоматически добавляет заголовок авторизации
- Компоненты фронтенда (дашборд, шаблоны, проекты) уже созданы и используют mock данные — требуется только замена источника данных
- refetchOnWindowFocus отключён для предотвращения ненужных запросов при переключении вкладок
- Стандартное время актуальности кэша — 5 минут, время жизни — 10 минут, для шаблонов — 30 минут
- Один повтор для неудавшихся запросов (queries), ноль повторов для мутаций
