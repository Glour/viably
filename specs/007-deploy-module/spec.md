# Feature Specification: Deploy Module

**Feature Branch**: `007-deploy-module`
**Created**: 2026-02-05
**Status**: Draft
**Input**: User description: "Railway deployment integration module based on docs/backend/deploy-module.md"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Deploy Project to Railway (Priority: P1)

Пользователь, который завершил генерацию кода для своего проекта, хочет развернуть бота на хостинг-платформе Railway одним нажатием кнопки. После ввода необходимых переменных окружения (BOT_TOKEN и др.) система автоматически создаёт проект на Railway, загружает код, настраивает окружение и запускает деплой.

**Why this priority**: Это основная функциональность модуля — без возможности деплоя пользователь не может запустить своего бота и получить рабочий продукт.

**Independent Test**: Можно протестировать путём создания проекта в статусе "ready" с сгенерированным кодом, вызова эндпоинта деплоя с валидным BOT_TOKEN и проверки, что бот становится доступен по публичному URL.

**Acceptance Scenarios**:

1. **Given** проект в статусе "ready" с сгенерированным кодом, **When** пользователь запрашивает деплой с валидными переменными окружения, **Then** система создаёт деплоймент и возвращает публичный URL бота
2. **Given** проект НЕ в статусе "ready", **When** пользователь запрашивает деплой, **Then** система возвращает ошибку с объяснением, что проект должен быть в статусе "ready"
3. **Given** проект без сгенерированного кода, **When** пользователь запрашивает деплой, **Then** система возвращает ошибку о необходимости сначала сгенерировать код

---

### User Story 2 - View Deployment Status (Priority: P2)

Пользователь хочет видеть текущий статус своего деплоймента — находится ли он в процессе сборки, деплоя, активен, остановлен или завершился с ошибкой. Это позволяет понимать, на каком этапе находится процесс развёртывания.

**Why this priority**: Без информации о статусе пользователь не может понять, успешно ли завершился деплой или нужно предпринять какие-то действия.

**Independent Test**: Можно протестировать путём создания деплоймента и проверки, что статус корректно отображается на каждом этапе (pending → building → deploying → active/failed).

**Acceptance Scenarios**:

1. **Given** существующий деплоймент пользователя, **When** пользователь запрашивает информацию о деплойменте, **Then** система возвращает актуальный статус, URL (если доступен) и время последнего обновления
2. **Given** несуществующий деплоймент или деплоймент другого пользователя, **When** пользователь запрашивает информацию, **Then** система возвращает ошибку "не найден"

---

### User Story 3 - View Deployment Logs (Priority: P2)

Пользователь хочет просматривать логи своего деплоймента для диагностики проблем — почему бот не запускается, какие ошибки возникают при сборке или выполнении.

**Why this priority**: Логи критически важны для отладки проблем, но являются вторичными по отношению к самому деплою и отображению статуса.

**Independent Test**: Можно протестировать путём создания деплоймента с логами и проверки, что логи корректно возвращаются пользователю.

**Acceptance Scenarios**:

1. **Given** активный деплоймент с логами, **When** пользователь запрашивает логи, **Then** система возвращает текстовые логи с временными метками
2. **Given** деплоймент без логов (pending статус), **When** пользователь запрашивает логи, **Then** система возвращает пустой ответ или сообщение об отсутствии логов

---

### User Story 4 - Stop/Delete Deployment (Priority: P3)

Пользователь хочет остановить и удалить свой деплоймент, когда бот больше не нужен или для экономии ресурсов.

**Why this priority**: Управление жизненным циклом деплоймента важно, но это действие выполняется реже, чем создание или мониторинг.

**Independent Test**: Можно протестировать путём создания активного деплоймента, его остановки и проверки, что ресурсы освобождены.

**Acceptance Scenarios**:

1. **Given** активный деплоймент пользователя, **When** пользователь запрашивает удаление, **Then** система удаляет проект на Railway и обновляет статус на "stopped"
2. **Given** несуществующий деплоймент, **When** пользователь запрашивает удаление, **Then** система возвращает ошибку "не найден"

---

### User Story 5 - Health Check (Priority: P3)

Система периодически проверяет работоспособность активных деплойментов, чтобы пользователь знал, жив ли его бот.

**Why this priority**: Health check — вспомогательная функция для мониторинга, не блокирующая основной функционал.

**Independent Test**: Можно протестировать путём создания активного деплоймента с публичным URL и выполнения health check запроса.

**Acceptance Scenarios**:

1. **Given** активный деплоймент с доступным URL, **When** выполняется health check, **Then** система обновляет время последней проверки и возвращает статус healthy/unhealthy
2. **Given** деплоймент с недоступным URL, **When** выполняется health check, **Then** система фиксирует неудачную проверку

---

### Edge Cases

- Что происходит, если Railway API недоступен во время деплоя? Система должна корректно обрабатывать таймауты и возвращать понятную ошибку.
- Что происходит, если деплой зависает дольше допустимого времени? Система должна иметь таймаут и переводить деплоймент в статус failed.
- Что происходит, если пользователь пытается создать второй деплоймент для того же проекта? Система должна либо отклонить запрос, либо остановить предыдущий деплоймент.
- Что происходит при ошибке на этапе сборки или деплоя? Система должна зафиксировать ошибку и сохранить сообщение для пользователя.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА создавать проект на платформе Railway при запросе деплоя
- **FR-002**: Система ДОЛЖНА создавать сервис внутри проекта Railway для размещения бота
- **FR-003**: Система ДОЛЖНА устанавливать переменные окружения (BOT_TOKEN и др.) для сервиса
- **FR-004**: Система ДОЛЖНА инициировать деплой сгенерированного кода на Railway
- **FR-005**: Система ДОЛЖНА отслеживать статус деплоя путём периодического опроса Railway API (интервал: 10 секунд)
- **FR-006**: Система ДОЛЖНА возвращать публичный URL в формате `https://{service-name}.up.railway.app` после успешного деплоя
- **FR-007**: Система ДОЛЖНА обновлять статус проекта на "deploying" при начале деплоя и "deployed" при успешном завершении
- **FR-008**: Система ДОЛЖНА сохранять информацию о деплойменте в базу данных (статус, URL, external_id, ошибки)
- **FR-009**: Система ДОЛЖНА позволять пользователю получить информацию о деплойменте по его ID
- **FR-010**: Система ДОЛЖНА позволять пользователю получить логи деплоймента
- **FR-011**: Система ДОЛЖНА позволять пользователю остановить и удалить деплоймент
- **FR-012**: Система ДОЛЖНА проверять права доступа — пользователь может управлять только деплойментами своих проектов
- **FR-013**: Система ДОЛЖНА обрабатывать ошибки Railway API и переводить деплоймент в статус "failed" с сохранением сообщения об ошибке
- **FR-014**: Система ДОЛЖНА иметь таймаут для деплоя (настраиваемый, по умолчанию 300 секунд) после которого деплой считается неудачным
- **FR-015**: Система ДОЛЖНА выполнять health check для активных деплойментов и сохранять время последней проверки
- **FR-016**: Система ДОЛЖНА позволять пользователю получить список всех своих деплойментов для проекта
- **FR-017**: При запросе нового деплоя для проекта с активным деплойментом система ДОЛЖНА автоматически остановить предыдущий деплоймент
- **FR-018**: Система ДОЛЖНА ограничивать частоту запросов деплоя: максимум 5 запросов в минуту на пользователя

### Non-Functional Requirements

- **NFR-001**: API эндпоинты ДОЛЖНЫ отвечать в течение 500ms (исключая polling и внешние вызовы)
- **NFR-002**: Логи деплоймента ДОЛЖНЫ храниться не более 30 дней
- **NFR-003**: Максимальный размер логов: 1MB на деплоймент
- **NFR-004**: Имя проекта Railway ограничено 50 символами (формат: `viably-{name:20}-{uuid:8}`)

### Deployment Status State Machine

```
pending → building → deploying → active
    ↓         ↓          ↓          ↓
  failed   failed     failed    stopped
```

**Переходы статусов**:
- `pending` → `building`: Railway начал сборку
- `building` → `deploying`: Сборка успешна, начат деплой
- `deploying` → `active`: Деплой успешен, URL доступен
- `* → failed`: Ошибка на любом этапе или таймаут
- `active → stopped`: Пользователь остановил деплоймент

### Key Entities

- **Deployment**: Запись о деплойменте проекта. Содержит: ID, связь с проектом, платформа (railway), внешний ID платформы, статус (pending/building/deploying/active/failed/stopped), публичный URL, URL логов сборки, URL админ-панели платформы, текст логов, сообщение об ошибке, метаданные платформы, временные метки создания/обновления/деплоя/последней проверки.

- **DeploymentStatus**: Статусы деплоймента:
  - `pending` — ожидание начала процесса
  - `building` — Railway выполняет сборку образа
  - `deploying` — образ собран, идёт развёртывание
  - `active` — деплоймент успешен, бот работает
  - `failed` — ошибка на любом этапе или таймаут
  - `stopped` — деплоймент остановлен пользователем

- **DeploymentPlatform**: Поддерживаемые платформы для деплоя — railway (основная), render (резерв).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может развернуть бота за менее чем 5 минут от момента запроса до получения рабочего URL
- **SC-002**: 95% успешных деплоев завершаются без ручного вмешательства
- **SC-003**: Пользователь получает уведомление о статусе деплоя (успех/ошибка) в течение 30 секунд после изменения
- **SC-004**: При ошибке деплоя пользователь получает понятное сообщение о причине в 100% случаев
- **SC-005**: Логи деплоя доступны пользователю в течение 10 секунд после запроса
- **SC-006**: Система корректно обрабатывает недоступность внешней платформы, возвращая понятную ошибку в течение 30 секунд

## Assumptions

- Railway API стабилен и доступен для интеграции (версия: GraphQL API v2)
- Бесплатного тарифа Railway достаточно для MVP (лимиты: 500 часов/месяц, 512MB RAM)
- BOT_TOKEN предоставляется пользователем, НЕ логируется и НЕ возвращается в API responses
- Один проект может иметь несколько деплойментов (история), но только один активный
- Health check выполняется как HTTP GET запрос на публичный URL деплоймента (healthy = HTTP status < 500)

## Error Messages Format

Все ошибки возвращаются в формате:
```json
{
  "detail": "Human-readable error message in Russian"
}
```

**Стандартные сообщения об ошибках**:
- Проект не найден: "Проект не найден"
- Проект не готов: "Проект должен быть в статусе 'ready' для деплоя"
- Нет кода: "Необходимо сначала сгенерировать код проекта"
- Деплоймент не найден: "Деплоймент не найден"
- Таймаут: "Превышено время ожидания деплоя (5 минут)"
- Railway недоступен: "Платформа Railway временно недоступна, попробуйте позже"
- Rate limit: "Превышен лимит запросов. Подождите минуту перед следующим деплоем"
