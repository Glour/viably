# Feature Specification: WebSocket & Generation Flow Integration

**Feature Branch**: `017-websocket-generation`
**Created**: 2026-02-07
**Status**: Draft
**Input**: User description: "WebSocket & Generation Flow integration - Real-time generation progress and deploy flow using WebSocket connections"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Real-time Generation Progress Monitoring (Priority: P1)

Пользователь запускает генерацию проекта и видит актуальный прогресс в реальном времени через WebSocket соединение вместо имитации прогресса.

**Why this priority**: Это основная функциональность, которая обеспечивает обратную связь пользователю о состоянии генерации. Без неё пользователь не знает, что происходит с его проектом.

**Independent Test**: Можно протестировать отдельно, запустив генерацию и проверив, что прогресс-бар обновляется на основе реальных событий от backend, а не таймера.

**Acceptance Scenarios**:

1. **Given** пользователь нажал "Генерировать" на странице проекта, **When** backend начинает генерацию, **Then** устанавливается WebSocket соединение и отображается прогресс первого шага
2. **Given** генерация выполняется, **When** backend переходит к следующему шагу, **Then** UI обновляет текущий шаг и процент выполнения
3. **Given** генерация выполняется, **When** backend отправляет фрагменты кода, **Then** фрагменты появляются в preview panel с анимацией typewriter
4. **Given** генерация завершена успешно, **When** приходит событие generation_complete, **Then** отображается сгенерированный код и кнопка Deploy
5. **Given** генерация завершена с ошибкой, **When** приходит событие generation_error, **Then** отображается сообщение об ошибке и кнопка Retry

---

### User Story 2 - WebSocket Connection Resilience (Priority: P1)

Пользователь продолжает получать обновления о генерации даже если соединение временно прерывается.

**Why this priority**: Критично для надёжности системы - генерация может занимать несколько минут, и за это время соединение может оборваться.

**Independent Test**: Можно протестировать отключив сеть на несколько секунд во время генерации и убедившись, что соединение восстанавливается автоматически.

**Acceptance Scenarios**:

1. **Given** WebSocket соединение активно, **When** соединение обрывается, **Then** система автоматически пытается переподключиться через 3 секунды
2. **Given** попытка переподключения не удалась, **When** прошло 3 секунды, **Then** система повторяет попытку с экспоненциальным backoff (6s, 12s, 24s, 48s)
3. **Given** выполнено 5 неудачных попыток переподключения, **When** достигнут лимит попыток, **Then** отображается ошибка "Потеряно соединение с сервером" с кнопкой "Попробовать снова"
4. **Given** пользователь переключился на другую вкладку браузера, **When** пользователь вернулся на вкладку, **Then** соединение автоматически восстанавливается, если было разорвано
5. **Given** генерация завершилась пока соединение было разорвано, **When** соединение восстановилось, **Then** UI обновляется до актуального состояния проекта

---

### User Story 3 - Deploy Flow with Real-time Feedback (Priority: P1)

Пользователь запускает деплой проекта и видит прогресс деплоя в реальном времени.

**Why this priority**: Деплой - ключевой момент в процессе создания бота. Пользователю важно видеть, что происходит на каждом этапе.

**Independent Test**: Можно протестировать запустив деплой и проверив, что все этапы (создание репозитория, push кода, build, health check) отображаются корректно.

**Acceptance Scenarios**:

1. **Given** пользователь заполнил environment variables в deploy modal, **When** нажата кнопка Deploy, **Then** отправляется запрос на деплой и устанавливается WebSocket соединение
2. **Given** деплой выполняется, **When** backend переходит к следующему этапу (Creating GitHub repo → Pushing code → Building container), **Then** UI обновляет текущий шаг и прогресс
3. **Given** деплой завершён успешно, **When** приходит событие deploy_complete, **Then** отображается информация о боте (bot username, Telegram ссылка, Railway URL) с конфетти
4. **Given** деплой завершён с ошибкой, **When** приходит событие deploy_error, **Then** отображается сообщение об ошибке и кнопка Retry
5. **Given** пользователь решил не деплоить, **When** всегда доступна кнопка Download ZIP, **Then** можно скачать код проекта локально

---

### User Story 4 - Credit Balance Updates via WebSocket (Priority: P2)

Баланс кредитов пользователя обновляется автоматически после списания или возврата средств.

**Why this priority**: Улучшает UX - пользователь сразу видит изменение баланса без перезагрузки страницы. Не критично для MVP, но важно для целостности системы.

**Independent Test**: Можно протестировать запустив генерацию и проверив, что баланс в navbar обновился после списания кредитов.

**Acceptance Scenarios**:

1. **Given** генерация завершена успешно, **When** backend отправляет credits_updated событие, **Then** баланс кредитов в navbar обновляется без перезагрузки страницы
2. **Given** генерация завершена с ошибкой, **When** backend возвращает кредиты (refund), **Then** баланс восстанавливается до прежнего значения
3. **Given** пользователь пополнил баланс в другой вкладке, **When** backend отправляет credits_updated, **Then** баланс обновляется во всех открытых вкладках

---

### User Story 5 - Generation Cancellation (Priority: P2)

Пользователь может отменить генерацию в любой момент.

**Why this priority**: Даёт контроль пользователю - если он понял, что ошибся с конфигурацией, можно не ждать завершения.

**Independent Test**: Можно протестировать запустив генерацию и нажав кнопку Cancel, убедившись что процесс остановлен и кредиты не списаны.

**Acceptance Scenarios**:

1. **Given** генерация выполняется, **When** пользователь нажимает кнопку Cancel, **Then** отправляется POST /api/projects/{id}/cancel-generation
2. **Given** запрос на отмену отправлен, **When** backend подтверждает отмену, **Then** WebSocket соединение закрывается и UI переходит в состояние idle
3. **Given** генерация отменена, **When** проверяется баланс кредитов, **Then** кредиты не списаны (или возвращены, если списание уже произошло)

---

### User Story 6 - Pre-Generation Credit Check (Priority: P1)

Пользователь видит стоимость генерации и не может запустить её при нехватке кредитов.

**Why this priority**: Предотвращает фрустрацию - пользователь сразу понимает, что нужно пополнить баланс.

**Independent Test**: Можно протестировать установив баланс меньше стоимости шаблона и проверив, что кнопка Generate disabled с соответствующим сообщением.

**Acceptance Scenarios**:

1. **Given** пользователь выбрал шаблон стоимостью 5 кредитов, **When** открыта страница генерации, **Then** на кнопке отображается "🚀 Генерировать (5 кредитов)"
2. **Given** баланс пользователя меньше стоимости шаблона, **When** открыта страница генерации, **Then** кнопка Generate disabled с текстом "Недостаточно кредитов ({have}/{need})"
3. **Given** баланс недостаточный, **When** отображается сообщение, **Then** есть ссылка "Пополнить →" ведущая на /settings/billing
4. **Given** пользователь пополнил баланс, **When** баланс обновился через credits_updated событие, **Then** кнопка Generate становится активной

---

### Edge Cases

- Что происходит, если WebSocket соединение не может установиться изначально? (Ответ: отображается ошибка "Не удалось подключиться к серверу" с возможностью retry)
- Как система обрабатывает сообщения, полученные в неожиданном порядке? (Ответ: каждое сообщение содержит step номер, UI игнорирует устаревшие сообщения)
- Что происходит, если пользователь закрывает вкладку во время генерации? (Ответ: генерация продолжается на backend, при возвращении на страницу проекта загружается актуальное состояние)
- Как обрабатывается ситуация, когда backend отправляет неизвестный тип сообщения? (Ответ: сообщение логируется в console.warn, но UI не ломается)
- Что происходит при превышении лимита reconnect попыток? (Ответ: отображается ошибка с кнопкой retry, которая сбрасывает счётчик попыток)
- Как система ведёт себя в offline режиме? (Ответ: отображается banner "Нет подключения к интернету", mutations disabled, auto-retry queries когда online)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА устанавливать безопасное авторизованное WebSocket соединение при запуске генерации
- **FR-002**: Система ДОЛЖНА парсить и обрабатывать 7 типов WebSocket сообщений: generation_progress, generation_complete, generation_error, deploy_progress, deploy_complete, deploy_error, credits_updated
- **FR-003**: Система ДОЛЖНА обновлять UI в реальном времени при получении events от backend через WebSocket
- **FR-004**: Система ДОЛЖНА автоматически переподключаться при обрыве соединения с экспоненциальным backoff (3s → 6s → 12s → 24s → 48s)
- **FR-005**: Система ДОЛЖНА ограничивать максимальное количество попыток переподключения до 5
- **FR-006**: Система ДОЛЖНА корректно закрывать WebSocket соединение при unmount компонента или отмене генерации
- **FR-007**: Система ДОЛЖНА отображать 6 шагов генерации: Analyzing template → Generating architecture → Writing code → Code review → Testing → Finalizing
- **FR-008**: Система ДОЛЖНА отображать 6 шагов деплоя: Creating GitHub repo → Pushing code → Connecting to Railway → Building container → Starting bot → Health check
- **FR-009**: Пользователи ДОЛЖНЫ иметь возможность отменить генерацию через кнопку Cancel
- **FR-010**: Система ДОЛЖНА проверять достаточность баланса кредитов перед началом генерации
- **FR-011**: Система ДОЛЖНА отображать стоимость генерации на кнопке Generate
- **FR-012**: Система ДОЛЖНА блокировать кнопку Generate при недостатке кредитов
- **FR-013**: Система ДОЛЖНА обновлять баланс кредитов в navbar при получении credits_updated события
- **FR-014**: Система ДОЛЖНА отображать сгенерированные фрагменты кода с анимацией typewriter в preview panel
- **FR-015**: Система ДОЛЖНА показывать конфетти при успешном завершении деплоя
- **FR-016**: Система ДОЛЖНА обрабатывать все API ошибки и отображать их через toast notifications
- **FR-017**: Система ДОЛЖНА обнаруживать offline состояние и отображать banner "Нет подключения к интернету"
- **FR-018**: Система ДОЛЖНА автоматически обновлять кэшированные данные после получения событий завершения
- **FR-019**: Система ДОЛЖНА сохранять и восстанавливать состояние генерации при переподключении WebSocket
- **FR-020**: Система ДОЛЖНА отображать deployment info (bot URL, username, Railway URL) после успешного деплоя

### Key Entities

- **WebSocket Connection**: Защищённое соединение с backend для получения real-time events, содержит идентификатор пользователя и токен авторизации, состояние (connected/disconnected), счётчик попыток переподключения
- **Generation Progress**: Состояние генерации проекта, включает номер текущего шага (1-6), название шага, статус (idle/generating/complete/error), прогресс (0-100), фрагменты кода, финальные файлы
- **Deploy Progress**: Состояние деплоя проекта, включает номер текущего шага (1-6), название шага, статус (idle/deploying/success/error), deployment info (platform, URL, bot username)
- **WebSocket Message**: Сообщение от backend, содержит тип (generation_progress/generation_complete/etc), project_id, data (step, step_name, step_status, progress, log, code_snippet)
- **Credit Balance**: Баланс кредитов пользователя, обновляется через WebSocket events, используется для pre-generation проверки

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь видит обновление прогресса генерации менее чем через 500ms после изменения на backend
- **SC-002**: WebSocket соединение автоматически восстанавливается в 95% случаев после кратковременного (до 30 секунд) обрыва
- **SC-003**: Фрагменты кода появляются в UI с визуальной анимацией typewriter менее чем через 1 секунду после получения
- **SC-004**: Баланс кредитов в navbar обновляется менее чем через 2 секунды после события credits_updated
- **SC-005**: Пользователь может успешно отменить генерацию на любом этапе с подтверждением в течение 3 секунд
- **SC-006**: Деплой от запуска до отображения bot URL занимает менее 5 минут в 90% случаев
- **SC-007**: Система корректно обрабатывает 100% типов WebSocket сообщений без падения UI
- **SC-008**: При недостатке кредитов кнопка Generate блокируется в 100% случаев до пополнения баланса
- **SC-009**: Offline banner появляется менее чем через 2 секунды после потери интернет-соединения
- **SC-010**: Конфетти анимация запускается в 100% случаев успешного деплоя

## Assumptions *(optional)*

- Backend API для генерации и деплоя уже реализован и готов к интеграции
- Система авторизации уже существует и предоставляет токены для защищённых соединений
- Backend может отправлять real-time события клиенту
- Код-редактор уже интегрирован для отображения сгенерированного кода
- Система управления состоянием приложения уже настроена
- Существует черновая версия генерации с имитацией прогресса, которую нужно заменить на реальную
- Платформа для деплоя проектов уже определена
- Стоимость генерации определяется конфигурацией шаблона проекта

## Dependencies *(optional)*

- **09-api-client-auth**: Нужны auth tokens для WebSocket авторизации
- **10-data-hooks**: Используются useProject, useCreateProject, useCreditBalance hooks
- **06-generation-flow**: UI компоненты для generation flow уже готовы и ждут подключения реальных hooks
- **Backend AI Generation Module (006)**: Должен отправлять WebSocket events в правильном формате
- **Backend Deploy Module (007)**: Должен отправлять deploy progress events

## Out of Scope *(optional)*

- Реализация серверной части WebSocket соединений (уже существует)
- Реализация backend логики генерации и деплоя (уже существуют)
- UI дизайн экранов генерации и деплоя (уже готов)
- Система биллинга и пополнения кредитов (уже существует)
- Интеграция с системами контроля версий для создания репозиториев (уже реализована)
- Интеграция с платформами для деплоя (уже реализована)
- Мониторинг и логирование соединений на production окружении (будет в отдельной задаче)
- WebSocket соединения для других функций кроме generation/deploy (будут использовать тот же механизм)
