# Feature Specification: Credits Module

**Feature Branch**: `003-credits-module`
**Created**: 2026-02-04
**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Расходование кредитов на генерацию контента (Priority: P1)

Пользователь хочет использовать кредиты для генерации контента (например, создание проекта). Система должна атомарно списать кредиты и зафиксировать транзакцию.

**Why this priority**: Это основная функциональность — без списания кредитов невозможно монетизировать сервис. Пользователи не смогут использовать платные функции.

**Independent Test**: Можно протестировать независимо, создав пользователя с кредитами и вызвав функцию списания. Результат — баланс уменьшается, транзакция записана.

**Acceptance Scenarios**:

1. **Given** пользователь имеет 10 кредитов, **When** система списывает 3 кредита за генерацию, **Then** баланс становится 7, создаётся запись транзакции с типом "generation"
2. **Given** пользователь имеет 2 кредита, **When** система пытается списать 5 кредитов, **Then** операция отклоняется с ошибкой "Недостаточно кредитов", баланс остаётся 2
3. **Given** два параллельных запроса на списание 5 кредитов у пользователя с балансом 5, **When** запросы выполняются одновременно, **Then** только один успешен, второй отклонён (защита от race condition)

---

### User Story 2 - Получение ежедневного бонуса (Priority: P1)

Пользователь с платной подпиской хочет получать ежедневный бонус кредитов. Бонус доступен раз в сутки и зависит от тарифного плана.

**Why this priority**: Ежедневные бонусы стимулируют регулярное использование сервиса и повышают вовлечённость. Критично для удержания пользователей.

**Independent Test**: Можно протестировать независимо через endpoint claim-daily-bonus. Результат — кредиты начислены, записано в историю.

**Acceptance Scenarios**:

1. **Given** пользователь на плане "starter" не получал бонус сегодня, **When** он запрашивает daily bonus, **Then** начисляется 3 кредита, записывается транзакция
2. **Given** пользователь уже получил бонус сегодня, **When** он повторно запрашивает бонус, **Then** запрос отклоняется с ошибкой "Бонус уже получен сегодня"
3. **Given** пользователь на бесплатном плане, **When** он запрашивает daily bonus, **Then** запрос отклоняется с ошибкой "План не включает ежедневные бонусы"

---

### User Story 3 - Начисление реферального бонуса (Priority: P2)

Когда новый пользователь регистрируется по реферальной ссылке, пригласивший получает бонусные кредиты.

**Why this priority**: Реферальная программа важна для органического роста, но не блокирует основной функционал.

**Independent Test**: Можно протестировать независимо, зарегистрировав нового пользователя с referral_code. Результат — referrer получает 5 кредитов.

**Acceptance Scenarios**:

1. **Given** пользователь A пригласил пользователя B, **When** пользователь B завершает регистрацию, **Then** пользователь A получает 5 кредитов, транзакция связана с пользователем B
2. **Given** пользователь регистрируется без реферальной ссылки, **When** регистрация завершена, **Then** реферальный бонус никому не начисляется

---

### User Story 4 - Применение месячного rollover-лимита (Priority: P2)

В начале каждого месяца система применяет лимиты переноса кредитов согласно тарифному плану пользователя.

**Why this priority**: Rollover предотвращает накопление чрезмерного количества кредитов и поддерживает бизнес-модель. Выполняется автоматически, не блокирует пользовательский функционал.

**Independent Test**: Можно протестировать независимо, запустив cron-задачу для пользователей с избыточным балансом. Результат — баланс урезан до лимита.

**Acceptance Scenarios**:

1. **Given** пользователь на плане "starter" имеет 250 кредитов, лимит 200, **When** выполняется месячный rollover, **Then** списывается 50 кредитов, баланс становится 200
2. **Given** пользователь на плане "pro" имеет 500 кредитов, лимит 600, **When** выполняется месячный rollover, **Then** баланс остаётся 500 (не превышает лимит)
3. **Given** пользователь на бесплатном плане имеет 10 кредитов, лимит 0, **When** выполняется месячный rollover, **Then** все 10 кредитов списываются, баланс становится 0

---

### User Story 5 - Просмотр информации о ежедневном бонусе (Priority: P3)

Пользователь хочет узнать доступность ежедневного бонуса и размер начисления.

**Why this priority**: Информационная функция, улучшает UX, но не критична для основного функционала.

**Independent Test**: Можно протестировать независимо через endpoint получения информации о бонусе. Результат — JSON с доступностью и суммой.

**Acceptance Scenarios**:

1. **Given** пользователь на плане "pro" не получал бонус сегодня, **When** он запрашивает информацию о бонусе, **Then** возвращается: amount=10, claimed_today=false, next_available_at=null
2. **Given** пользователь получил бонус сегодня, **When** он запрашивает информацию, **Then** возвращается: claimed_today=true, next_available_at="завтра 00:00 UTC"

---

### Edge Cases

- Что происходит при попытке списания отрицательного количества кредитов? → Отклоняется валидацией (amount > 0)
- Что происходит при добавлении кредитов пользователю, который не существует? → Ошибка "Пользователь не найден"
- Что происходит если cron-задача rollover падает посередине обработки? → Каждый пользователь обрабатывается в отдельной транзакции, обработанные остаются с корректным балансом
- Что происходит при смене плана пользователя между daily bonus claims? → Размер бонуса берётся из текущего плана на момент claim
- Что происходит если referrer удалён после того как referee зарегистрировался? → Бонус не начисляется (user_id не найден)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА атомарно списывать кредиты с блокировкой на уровне записи пользователя
- **FR-002**: Система ДОЛЖНА отклонять списание при недостаточном балансе с кодом ошибки 422
- **FR-003**: Система ДОЛЖНА записывать каждую операцию с кредитами в историю транзакций
- **FR-004**: Система ДОЛЖНА атомарно начислять кредиты с записью транзакции
- **FR-005**: Пользователи ДОЛЖНЫ иметь возможность получить ежедневный бонус (если план включает)
- **FR-006**: Система ДОЛЖНА ограничивать получение ежедневного бонуса до одного раза в сутки (по UTC)
- **FR-007**: Размер ежедневного бонуса ДОЛЖЕН зависеть от тарифного плана: free=0, starter=3, pro=10, business=20
- **FR-008**: Система ДОЛЖНА начислять реферальный бонус (5 кредитов) при регистрации нового пользователя по реферальной ссылке
- **FR-009**: Система ДОЛЖНА выполнять месячный rollover 1-го числа каждого месяца в 00:00 UTC
- **FR-010**: Rollover-лимиты ДОЛЖНЫ быть: free=0, starter=200, pro=600, business=2000
- **FR-011**: Система ДОЛЖНА защищать от race conditions при параллельных операциях с кредитами
- **FR-012**: Каждая транзакция ДОЛЖНА содержать: user_id, amount, balance_after, transaction_type, created_at
- **FR-013**: Типы транзакций ДОЛЖНЫ включать: signup, daily_bonus, referral_bonus, purchase, refund, generation, rollover, admin_adjustment

### Key Entities *(include if feature involves data)*

- **CreditTransaction**: Запись операции с кредитами — содержит сумму (положительную для начисления, отрицательную для списания), баланс после операции, тип операции, опциональные связи с проектом и пользователем (для рефералов)
- **DailyBonus**: Запись о полученном ежедневном бонусе — связана с пользователем, содержит дату и сумму начисления, уникальна по комбинации user_id + bonus_date

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователи могут списать или начислить кредиты менее чем за 1 секунду
- **SC-002**: 100% операций с кредитами записываются в историю транзакций без потерь
- **SC-003**: При параллельных запросах списания на один аккаунт ни одна операция не приводит к отрицательному балансу
- **SC-004**: 100% пользователей с платными планами могут успешно получить ежедневный бонус раз в сутки
- **SC-005**: Месячный rollover обрабатывает всех пользователей без ручного вмешательства
- **SC-006**: 100% реферальных бонусов корректно начисляются при регистрации по реферальной ссылке
- **SC-007**: Все функции модуля покрыты тестами на >90%

## Assumptions

- Пользователь уже имеет поле `credits` (integer) и `plan` (string) в своей записи (из Users Module)
- Пользователь уже имеет поле `referral_code` и механизм отслеживания рефералов (из Users Module)
- Часовой пояс для daily bonus и rollover — UTC
- Стартовый бонус при регистрации (signup credits) обрабатывается в Users Module, а не в Credits Module
- Проект (Project) как сущность существует и имеет id (для связи с транзакциями generation)
